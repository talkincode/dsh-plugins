# dsh-plugins 项目画像与方向

## 项目概述

`dsh-plugins` 是一个 **DSH 插件集仓库**：用来承载可被 agent 运行时（例如 Mira 或其他兼容宿主）本地加载的三类资产 —— **技能（skills）**、**MCP（Model Context Protocol）定义**，以及未来面向人类操作者的**管理 UI**。它不是一个要发布到公共包管理器的库，而是一个"仓库内即用"的插件登记与分发中心：新增一个能力 = 新增一个自包含目录，不需要额外的打包、发版、上传步骤。

服务对象是需要给 agent 运行时扩展能力的开发者和维护者：他们在这个仓库里新增/维护 skill 或 MCP 定义，宿主运行时直接从仓库路径加载，无需经过任何注册表中转。

当前仓库处于**初始化阶段**：只有目录约定和规划文档，尚未包含任何真正运行的技能、MCP 定义或管理 UI 实现（详见"当前能力清单"）。

架构图（目标形态，非当前已实现状态）：

```text
dsh-plugins/
├── skills/                 # 一技能一目录，自包含
│   └── <skill-id>/
│       ├── SKILL.md        # 技能说明（做什么、何时用、如何调用）
│       └── ...             # 脚本、资源、示例，全部与 SKILL.md 同目录
├── mcp/                    # MCP server / 工具定义的本地登记
│   └── <mcp-id>/           # 每个 MCP 登记项自成一目录（约定，具体 schema 待定）
├── docs/
│   └── roadmap.md          # 本文档：项目画像与方向（唯一事实来源）
├── AGENTS.md                # 开发规约：目录、边界、脱敏硬规则
└── (未来) 管理 UI            # 预留，浏览/审阅 skills 与 mcp 登记项，未锁定技术栈
```

外部依赖：无强制外部服务。宿主运行时（Mira 或其他 agent runtime）通过本地文件路径发现并加载 `skills/` 与 `mcp/` 下的内容，不经过网络注册表。

## 项目画像（目标状态）

做好之后，`dsh-plugins` 应该是这样的：

- **自包含优先**：任何一个 `skills/<skill-id>/` 目录都可以被单独复制到别处继续工作，不依赖仓库里其他目录的隐藏耦合。
- **零发布摩擦**：新增/修改一个技能或 MCP 登记项，改完提交即可用，不需要 `npm publish`、版本号协商或等待任何外部注册表同步。
- **可发现优先于炫技**：目录结构和 README 索引比实现的精巧程度更重要——任何人打开仓库都能在一分钟内看懂"有哪些技能/MCP、在哪、怎么用"。
- **脱敏优先于示例便利性**：宁可示例数据难看、占位符啰嗦，也不允许任何真实密钥、内网信息、客户数据出现在仓库任何角落（代码、文档、日志、fixture、截图、commit message、PR、Issue 皆在此列）。
- **渐进式管理面**：管理 UI 是方向而非当前任务，一旦启动实现，也不应把它锁死在某一套前端/后端技术栈上——先满足"能看、能审"的最小诉求，具体框架留给实现者决定。

当这些品质发生冲突时的优先级：**安全（脱敏）> 自包含（不依赖发布基础设施）> 实现速度 / 技术栈自由**。也就是说，即便某个便利做法能让示例更好看或让管理 UI 更快上线，只要它依赖真实数据或依赖外部发布通道，就不被采纳。

## 当前能力清单

仓库目前处于**纯规划/骨架阶段**，以下是已经存在、有据可查的内容：

- **仓库基础文件**：`README.md`、`LICENSE`（MIT）。
- **规划文档**：`docs/roadmap.md`（本文档）与 `AGENTS.md`，定义目录约定、边界与脱敏规则。
- **目录占位**：`skills/`、`mcp/` 已建立，各自带 `README.md` 说明用途和约定，但**不含任何真正实现的技能或 MCP 定义**（占位说明本身不是功能）。

以下能力**尚未建立**，不要误认为已存在：

- 没有任何可运行的技能（`skills/` 下无实际 SKILL.md 实现，仅有约定说明）。
- 没有任何 MCP server/工具定义的实际登记内容。
- 没有管理 UI（无前端、无后端、无 API）。
- 没有 CI、没有自动化脱敏扫描、没有测试基础设施（待核验/未建立）。

## 非目标（铁律）

- **不以 npm registry（或任何公共包管理器）作为分发通道。** 不建立 `npm publish` 流程，不把"发布到公共包管理器"设为里程碑或目标。技能与 MCP 定义只通过仓库本身分发，宿主运行时直接从本地路径加载。
- **不允许技能脱离自包含约束。** 每个技能必须是"一技能一目录"：`SKILL.md`、脚本、资源全部放在同一个 `skills/<skill-id>/` 目录下；禁止让一个技能运行时依赖仓库其他目录中的私有资源。
- **不提交任何真实敏感数据。** 禁止在任何提交、示例、日志、截图、fixture、Issue、PR、文档中出现真实密钥、token、cookie、密码、内网地址清单、客户标识、账号，或完整配置中的秘密字段。示例只能使用假数据或占位符；如果现有素材含疑似秘密，必须先脱敏处理，禁止原样写入 git 历史。
- **当前阶段不实现完整管理 UI。** 管理面处于"方向与意图"，不是当前交付范围；也不允许提前把它锁定在某个具体前端框架/后端技术栈上，为后续实现留出选择空间。
- **管理 UI（一旦实现）默认按脱敏展示连接/配置信息。** 名称与状态类信息可以直接显示，但任何秘密值只能写入（配置/更新），不能被读出或回显。

## 方向与意图

- **插件体系**：让 `skills/`、`mcp/` 成为宿主运行时可信赖的本地扩展点——新增一个能力就是新增一个自包含目录 + 登记说明，不需要中心化审批或发布流程。这服务于"零发布摩擦"和"自包含优先"的画像。
- **Skills 管理**：随着技能数量增长，需要某种方式让贡献者和运行时都能"发现有哪些技能、是否自包含、是否含疑似秘密"。具体实现（索引文件、校验脚本、CI 检查）留给后续实现者选择，不在本文档锁定格式。
- **MCP 管理**：`mcp/` 目录承载 MCP server/工具定义的本地登记信息。未来可能需要一份清单或 schema 来描述每个 MCP 登记项的元数据，具体结构留给后续实现决定。
- **管理面（预留）**：未来可能出现一个面向人类操作者的管理界面，用于浏览、启停、审阅 skills 与 mcp 登记项。这是方向，不是当前任务范围；它不预先锁定具体前端/后端技术栈，但必须遵守"默认脱敏展示"的铁律。

## 完成的样子

- 新增一个技能时，贡献者只需在 `skills/<skill-id>/` 下工作，不必触碰仓库其他目录；该目录本身可以被整体复制到别处继续独立使用。
- 新增一个 MCP 登记项时，贡献者能在 `mcp/` 下找到清晰的位置和说明，不必依赖任何外部发布步骤。
- 任何人审阅一次提交或 PR 时，能够确认其中不含真实密钥、内网地址或客户数据——具体审查手段（pre-commit hook、CI 扫描脚本、人工 checklist）留给后续实现选择，但至少要存在一种机制。
- 管理 UI 真正出现时，展示层默认隐藏秘密值，只有名称、状态等非敏感信息直接可见。

## 验收矩阵（业务能力覆盖矩阵）

> 覆盖底线（硬性规定，写入 `AGENTS.md` 同步生效）：
>
> 1. 每个一级功能至少有一条 Happy Path 的 E2E 验证。
> 2. 每个高风险功能至少覆盖一条失败路径。
> 3. 每个涉及权限的功能至少验证两种角色（如管理员/普通用户，或有权/无权）。
> 4. 每个会修改系统状态的操作至少验证一次失败后的恢复或回滚。
> 5. 每次新增一级业务功能，必须同步新增对应的 E2E 并登记进本矩阵。

| 一级功能 | 风险级别 | Happy Path E2E | 失败路径 | 权限角色覆盖 | 失败恢复/回滚 | 证据（测试路径/用例） |
| --- | --- | --- | --- | --- | --- | --- |
| 插件/技能自包含加载约定 | 中 | ❌ 缺口 | 不适用（目前无运行时代码） | 不适用（无角色概念，纯目录约定） | 不适用（无状态变更操作） | 待建立：首个示例技能 + 自包含性校验脚本 |
| Skills 管理（登记/发现） | 中 | ❌ 缺口 | 不适用 | 不适用 | 不适用 | 待建立：`skills/` 索引或校验工具 |
| MCP 管理（本地登记） | 中 | ❌ 缺口 | 不适用 | 不适用 | 不适用 | 待建立：`mcp/` 登记 schema 与校验 |
| 管理 UI（预留） | 中 | 不适用（尚未规划实现，处于方向与意图阶段） | 不适用 | 不适用（未来若涉及权限管理需补充两种角色验证） | 不适用 | 尚未启动 |
| 提交脱敏检查 | 高（防止真实密钥/客户数据泄露） | ❌ 缺口 | ❌ 缺口 | 不适用（对所有贡献者一视同仁） | 不适用（只读检查，不修改系统状态） | 待建立：脱敏扫描机制（如 pre-commit/CI hook） |

对每个 ❌ 缺口的最低期望：

- **插件/技能自包含加载约定、Skills 管理、MCP 管理**：在首个真正的技能/MCP 登记项落地时，必须同步补上至少一条端到端验证（例如"运行时能否从该目录成功加载并调用"），并在本表登记证据路径。
- **提交脱敏检查**：在引入任何自动化脱敏扫描前，至少要有一份人工 PR checklist 明确写出"不得包含真实密钥/内网信息/客户数据"，作为过渡期最低保障；自动化机制上线后须补充失败路径验证（即扫描确实能拦下一个含疑似秘密的示例提交）。
