# dsh-plugins 项目画像与方向

## 项目概述

`dsh-plugins` 是一个 **DSH 插件集合项目**：用来集中登记、发现、管理各类可被 agent 运行时（例如 Mira 或其他兼容宿主）使用的插件。它的主体是"插件的集合与后续扩展"，不是某一类特定资产（如 skills 或 MCP）的专属实现仓库，也不把"管理 skills 和 MCP"当作自身职责的全部。

插件可以来自不同类别（技能、MCP 工具、未来可能出现的其他扩展形态），每个插件在仓库里对应一个自包含的子目录（**一插件一目录**）。插件的真实实现来源可以是仓库内联代码，也可以是指向外部代码库的登记信息——本仓库不强制把所有插件的完整实现搬进来，它做的是集合与管理，不是把各来源仓库整包吞并。

初期阶段规划了两类**管理面**能力：Skills 管理（面向技能类插件的登记/浏览/审阅）与 MCP 管理 UI（面向 MCP 类插件的登记/浏览/审阅）。这两者是本项目在插件集合之上提供的**管理能力**，不是项目本身的定位；管理面展示的是登记信息（名称、状态、类型、指向），不等同于把被管理对象的实现搬进本仓库。

服务对象是需要维护、发现、审阅多类 agent 扩展能力的开发者和维护者：他们在 `plugins/` 下新增/维护插件登记项，宿主运行时或管理面从仓库路径读取这些登记信息。

当前仓库处于**初始化阶段**：只有目录约定和规划文档，尚未包含任何真正落地的插件、管理面实现。

架构图（目标形态，非当前已实现状态）：

```text
dsh-plugins/
├── plugins/                 # 插件集合：一插件一目录，自包含登记
│   └── <plugin-id>/
│       ├── PLUGIN.md         # 插件说明：类型（skill/MCP/其他）、如何加载、实现指向哪里
│       └── ...                # 仅当插件足够小、适合内联时才放脚本/资源
├── docs/
│   └── roadmap.md            # 本文档：项目画像与方向（唯一事实来源）
├── AGENTS.md                  # 开发规约：目录、边界、脱敏硬规则
└── (未来) 管理 UI              # 预留，面向 Skills / MCP 等插件类型的登记浏览与审阅，未锁定技术栈
```

外部依赖：无强制外部服务。宿主运行时或管理面通过本地文件路径发现并读取 `plugins/` 下的登记内容，不经过网络注册表；插件实现若在外部代码库，登记项里只保留指向信息，不代管该代码库的发布流程。

## 项目画像（目标状态）

做好之后，`dsh-plugins` 应该是这样的：

- **集合优先于专仓**：仓库的核心资产是"插件的集合"，覆盖多种插件类型；不应该被误解或收窄为"skills 和 MCP 的专属实现仓库"。新增一种插件类型不需要改变项目定位。
- **一插件一目录、自包含登记**：任何一个 `plugins/<plugin-id>/` 目录都能被单独查看、理解其类型和加载方式，不依赖仓库里其他目录的隐藏耦合；实现代码如果在外部来源，登记项本身依然自包含（指向信息完整、不缺失）。
- **登记与实现分离**：本仓库负责"知道有哪些插件、它们是什么类型、去哪里找实现、当前状态如何"，不负责代管所有插件的源码全集。管理面（Skills 管理、MCP 管理 UI）只做登记、浏览、审阅，不越界成为实现仓库。
- **零发布摩擦**：新增/修改一个插件登记项，改完提交即可用，不需要 `npm publish`、版本号协商或等待任何外部注册表同步。
- **可发现优先于炫技**：目录结构和登记信息比实现的精巧程度更重要——任何人打开仓库都能在一分钟内看懂"有哪些插件、什么类型、在哪、去哪找实现"。
- **脱敏优先于示例便利性**：宁可示例数据难看、占位符啰嗦，也不允许任何真实密钥、内网信息、客户数据出现在仓库任何角落（代码、文档、日志、fixture、截图、commit message、PR、Issue 皆在此列）。
- **渐进式管理面**：管理 UI 是方向而非当前任务，一旦启动实现，也不应把它锁死在某一套前端/后端技术栈上，也不应该只覆盖 skills/MCP 两种类型而排斥未来的插件类型——先满足"能看、能审"的最小诉求，具体框架和覆盖范围留给实现者按需扩展。

当这些品质发生冲突时的优先级：**安全（脱敏）> 定位准确（不被收窄为专仓）> 自包含登记（不依赖发布基础设施）> 实现速度 / 技术栈自由**。也就是说，即便某个便利做法能让管理面更快上线，只要它需要把某类插件的完整实现强行搬进本仓库，或依赖真实数据、外部发布通道，就不被采纳。

## 当前能力清单

仓库目前处于**纯规划/骨架阶段**，以下是已经存在、有据可查的内容：

- **仓库基础文件**：`README.md`、`LICENSE`（MIT）。
- **规划文档**：`docs/roadmap.md`（本文档）与 `AGENTS.md`，定义目录约定、边界与脱敏规则。
- **目录占位**：`plugins/` 已建立，带 `README.md` 说明"一插件一目录、登记优先于搬运"的约定，但**不含任何真正落地的插件登记项**（占位说明本身不是功能）。

以下能力**尚未建立**，不要误认为已存在：

- 没有任何真正落地的插件登记项（`plugins/` 下无实际 `PLUGIN.md` 实现，仅有约定说明）。
- 没有 Skills 管理面、没有 MCP 管理 UI（无前端、无后端、无 API）。
- 没有 CI、没有自动化脱敏扫描、没有测试基础设施（待核验/未建立）。

## 非目标（铁律）

- **本仓库不是 skills/MCP 专仓。** 项目定位是"插件集合"，覆盖但不限于技能类、MCP 类插件；不得把项目职责收窄描述为"专门管理 skills 和 MCP"，也不得因为初期只规划了这两类管理面就把项目重新定义为二者的专属仓库。
- **不把技能/MCP 的完整实现代码整包塞进本仓库目录当作默认动作。** 插件的真实实现允许维护在外部代码库；`plugins/<plugin-id>/` 下默认放登记/配置说明（指向哪里、暴露什么能力），只有足够小、适合内联的插件才把完整实现放进来。禁止以"落地全部 skills/MCP"为目标去搬运外部实现仓库的源码全集。
- **一插件一目录，不允许再退回"一技能一目录 / 一 MCP 一目录"作为仓库资产落地骨架。** `plugins/<plugin-id>/` 是本仓库唯一的资产落地约定；不新建独立的 `skills/`、`mcp/` 顶层目录作为技能或 MCP 的专属存放地。
- **不以 npm registry（或任何公共包管理器）作为分发通道。** 不建立 `npm publish` 流程，不把"发布到公共包管理器"设为里程碑或目标。插件登记项只通过仓库本身分发，宿主运行时或管理面直接从本地路径加载。
- **不提交任何真实敏感数据。** 禁止在任何提交、示例、日志、截图、fixture、Issue、PR、文档中出现真实密钥、token、cookie、密码、内网地址清单、客户标识、账号，或完整配置中的秘密字段。示例只能使用假数据或占位符；如果现有素材含疑似秘密，必须先脱敏处理，禁止原样写入 git 历史。
- **当前阶段不实现完整管理 UI。** 管理面处于"方向与意图"，不是当前交付范围；也不允许提前把它锁定在某个具体前端框架/后端技术栈上，也不允许提前把它的覆盖范围锁死为"只服务 skills 和 MCP 两类"，为后续插件类型扩展留出选择空间。
- **管理 UI（一旦实现）默认按脱敏展示连接/配置信息。** 名称与状态类信息可以直接显示，但任何秘密值只能写入（配置/更新），不能被读出或回显。

## 方向与意图

- **插件集合体系**：让 `plugins/` 成为宿主运行时和维护者都可信赖的插件登记中心——新增一种插件类型或一个具体插件，就是新增一个自包含的登记目录，不需要中心化审批或发布流程，也不需要改变项目定位。这服务于"集合优先于专仓"和"登记与实现分离"的画像。
- **Skills 管理（管理面之一）**：面向技能类插件，提供登记、发现、浏览、审阅能力，帮助贡献者和运行时确认"有哪些技能类插件、指向哪里、是否含疑似秘密"。这是插件集合之上的一个管理面能力，不代表本仓库要代管所有技能的实现源码。具体实现（索引文件、校验脚本、CI 检查、UI 呈现）留给后续实现者选择。
- **MCP 管理 UI（管理面之一）**：面向 MCP 类插件，提供登记、发现、浏览、审阅能力。同样是管理面能力而非实现仓库；未来可能需要一份清单或 schema 描述每个 MCP 登记项的元数据，具体结构留给后续实现决定。
- **管理面的可扩展性**：随着插件类型增多，管理面应当能够扩展覆盖新的插件类型，而不是被锁死为"只认识 skills 和 MCP"。这是方向，不是当前任务范围；它不预先锁定具体前端/后端技术栈，但必须遵守"默认脱敏展示"的铁律。

## 完成的样子

- 新增一个插件时，贡献者只需在 `plugins/<plugin-id>/` 下工作，写清楚类型和实现指向，不必触碰仓库其他目录；即使实现在外部代码库，登记信息本身也是完整、自包含的。
- 任何人打开仓库都能一眼看出"这是一个插件集合项目"，而不会误以为它是 skills 或 MCP 的专属实现仓库。
- 任何人审阅一次提交或 PR 时，能够确认其中不含真实密钥、内网地址或客户数据——具体审查手段（pre-commit hook、CI 扫描脚本、人工 checklist）留给后续实现选择，但至少要存在一种机制。
- 管理 UI 真正出现时，能够浏览 Skills、MCP 等多类插件的登记信息，展示层默认隐藏秘密值，只有名称、状态、类型等非敏感信息直接可见；新增一种插件类型时管理面可以扩展覆盖，不需要推倒重来。

## 验收矩阵（业务能力覆盖矩阵）

> 覆盖底线（硬性规定，写入 `AGENTS.md` 同步生效）：
>
> 1. 每个一级功能至少有一条 Happy Path 的 E2E 验证。
> 2. 每个高风险功能至少覆盖一条失败路径。
> 3. 每个涉及权限的功能至少验证两种角色（如管理员/普通用户，或有权/无权）。
> 4. 每个会修改系统状态的操作至少验证一次失败后的恢复或回滚。
> 5. 每次新增一级业务功能，必须同步新增对应的 E2E 并登记进本矩阵。

| 一级功能 | 风险级别 | Happy Path E2E | 失败路径 | 权限角色覆盖 | 失败恢复/回滚 | 证据（测试路径/用例） |
| --- | --- | --- | --- | --- | --- | --- |
| 插件集合登记（一插件一目录） | 中 | ❌ 缺口 | 不适用（目前无运行时代码） | 不适用（无角色概念，纯目录约定） | 不适用（无状态变更操作） | 待建立：首个示例插件 + 自包含性/指向有效性校验脚本 |
| Skills 管理面（登记/浏览/审阅） | 中 | ❌ 缺口 | 不适用 | 不适用 | 不适用 | 待建立：技能类插件索引或校验工具 |
| MCP 管理 UI（登记/浏览/审阅） | 中 | ❌ 缺口 | 不适用 | 不适用 | 不适用 | 待建立：MCP 类插件登记 schema 与校验 |
| 提交脱敏检查 | 高（防止真实密钥/客户数据泄露） | ❌ 缺口 | ❌ 缺口 | 不适用（对所有贡献者一视同仁） | 不适用（只读检查，不修改系统状态） | 待建立：脱敏扫描机制（如 pre-commit/CI hook） |

对每个 ❌ 缺口的最低期望：

- **插件集合登记、Skills 管理面、MCP 管理 UI**：在首个真正的插件登记项落地时，必须同步补上至少一条端到端验证（例如"运行时或管理面能否从该登记项正确识别类型与实现指向"），并在本表登记证据路径。
- **提交脱敏检查**：在引入任何自动化脱敏扫描前，至少要有一份人工 PR checklist 明确写出"不得包含真实密钥/内网信息/客户数据"，作为过渡期最低保障；自动化机制上线后须补充失败路径验证（即扫描确实能拦下一个含疑似秘密的示例提交）。
